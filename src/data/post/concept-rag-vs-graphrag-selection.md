# RAG vs GraphRAG 选型决策:什么时候上、什么时候不上

> 80% 团队默认上 GraphRAG 但其实用不上,20% 团队应该上但没用 — 本文给一个不拍脑袋的决策框架。

## 为什么写这篇

在 RAG 圈子里,「上不上图」是个反复出现的争议话题。一边是「GraphRAG 万能论」,看到关系二字就兴奋;另一边是「向量检索够用论」,觉得图谱纯属过度工程。

我的观察是:**大部分团队在错误的地方花了大价钱**。

- 简单 FAQ 场景,上 GraphRAG,索引烧了几百美元 LLM token,答案质量跟纯向量检索几乎一样。
- 复杂法律/医疗场景,只上向量检索,用户问「这家公司跟那家公司有什么关联」,答得一塌糊涂。

问题不是「GraphRAG 好不好」,而是「**这个场景该不该上 GraphRAG**」。本文目标:给你 4 个评分维度的决策框架 + 5 个真实场景的判断 + 7 条避坑清单。看完后,你能对自己的场景给出「上」/「不上」/「混合」的明确答案。

## 一、RAG 的能力边界

先把 vanilla RAG(纯向量检索 + LLM)的能力画清楚,再谈 GraphRAG 才公平。

### 擅长的事

| 能力 | 说明 | 典型例子 |
|------|------|----------|
| **相似度召回** | 找到与 query 语义最接近的 top-k chunks | "文档里有没有讲 GraphRAG 索引成本的段落" |
| **单文档 QA** | 围绕一段/一篇文档的事实问答 | "这段代码为什么这么写" |
| **关键词检索的语义升级** | 比 BM25 多了语义理解 | "找出所有讲 RAG 痛点的章节" |
| **低延迟** | 向量检索毫秒级,LLM 1-3 秒 | 在线客服、IDE 助手 |
| **零索引成本** | 文档 embedding 一次即可 | 几百到几千文档的小项目 |

### 不擅长的事(也就是 GraphRAG 的发力点)

**1. 全局性问题(holistic question)**

```
问: "我们公司 2025 年所有项目的主题分布如何?"

向量检索的应对:
  query → embedding → 找 top-5 相似 chunks → LLM 综合
  ↓
  top-5 是"最像"query 的 5 个,不是"全部"
  答:"大概集中在 AI 和数据这两个主题"(可能漏掉其他 80%)
```

这类问题需要**全库聚合**,top-k 永远只能给局部视图。

**2. 实体关系(relationship chain)**

```
问: "A 公司 CEO 之前在哪家公司工作过?"

向量检索的应对:
  找"CEO"相关 chunk → 抽名字 → 再找"X 公司"相关 chunk
  ↓
  如果 CEO 履历在文档 A,公司 X 简介在文档 B,中间没有任何 chunk 把两者串起来 → 答不上
```

关系藏在文本里,没有结构化。

**3. 多跳推理(multi-hop)**

```
问: "A 项目用了 B 库,B 库依赖 C 库,C 库的核心开发者是 D — D 现在在哪家公司?"

向量检索的应对:每一跳都可能丢上下文,3 跳之后基本是赌博
```

**4. 时序/演化(time-series evolution)**

```
问: "这个产品从 2023 到 2025 年的功能变化?"

向量检索的应对:找到的 chunks 是"全部时间点的相似结果",无法按时序拼出"变化"
```

## 二、GraphRAG 的能力边界

GraphRAG 也不是银弹。**它在解决上面 4 个痛点的同时,引入了 4 个新成本**。

### 解决的问题

- ✅ 全局性问题(Global Search 用社区摘要聚合)
- ✅ 实体关系(Local Search 用 k-hop 邻居展开)
- ✅ 多跳推理(图遍历天然适合)
- ✅ 跨文档聚合(社区检测 + LLM 摘要)

### 引入的代价

| 代价 | 量级 | 备注 |
|------|------|------|
| **索引成本** | 1k 文档需要 50-500 美元 LLM token | 微软官方数据 + 实测估算 |
| **索引时间** | 1k 文档 1-6 小时 | 取决于 LLM 并发和文档长度 |
| **存储膨胀** | 图 + 向量 + 社区摘要,可能比原文大 5-20 倍 | Neo4j 部署需要规划 |
| **查询延迟** | 比纯向量慢 2-5 倍 | 多了一次图遍历 + LLM 调用 |
| **LLM 抽取错误** | 实体识别准确率 80-95% | 关键实体错了全盘皆输 |
| **增量更新难** | 加 100 篇文档要重跑全量 or 写复杂增量逻辑 | 微软 GraphRAG 增量还不成熟 |
| **调参复杂** | chunk size、prompt、prompt 模板、合并阈值都要调 | 没有银弹参数 |

**关键判断**:GraphRAG 的价值在「**关系密度高**」的语料上才显著。如果语料里实体之间没什么结构化关系,索引一遍只是浪费钱。

## 三、4 维评分决策框架

不要凭感觉上不上,量化打分。下面 4 个维度,每个 0-3 分,总分 ≥ 8 分强烈建议上 GraphRAG,5-7 分看预算,≤ 4 分纯向量检索够用。

### 维度 1:问题类型(0-3 分)

| 问题类型 | 分数 | 例子 |
|----------|------|------|
| 纯相似度查询 | 0 | "文档里讲 RAG 的章节" |
| 单实体事实查询 | 1 | "GraphRAG 是谁开源的" |
| 多实体关系查询 | 2 | "A 公司收购了哪些公司" |
| 全局聚合问题 | 3 | "2025 年所有项目的技术栈分布" |

### 维度 2:语料规模(0-3 分)

| 文档数 | 分数 | 理由 |
|--------|------|------|
| < 500 | 0 | 向量检索完全够,图谱增益不明显 |
| 500 - 5k | 1 | 边界,可上可不上 |
| 5k - 50k | 2 | 进入 GraphRAG 甜蜜区 |
| > 50k | 3 | 必须考虑图谱(否则 token 爆炸) |

### 维度 3:关系密度(0-3 分)

**关系密度 = 文档中能抽取出的实体关系数 / 文档数**

| 关系密度 | 分数 | 典型语料 |
|----------|------|----------|
| < 5 关系/文档 | 0 | 通用 FAQ、产品手册 |
| 5-20 关系/文档 | 1 | 新闻文章、技术博客 |
| 20-50 关系/文档 | 2 | 学术论文、企业年报 |
| > 50 关系/文档 | 3 | 知识库、人物关系网、供应链 |

> 💡 **关键判断**:如果语料主要是"叙述性文本"(博客、新闻),关系密度天然低;如果语料是"结构化叙述"(年报、论文、合同),关系密度天然高。

### 维度 4:查询模式(0-3 分)

| 查询特征 | 分数 |
|----------|------|
| 90% 查询是单跳相似度 | 0 |
| 50% 查询需要 2-3 跳 | 1 |
| 30% 查询需要 3+ 跳或聚合 | 2 |
| 大量"总结/对比/趋势"类问题 | 3 |

### 总分判定

| 总分 | 建议 |
|------|------|
| 0-4 | 纯向量 RAG,别折腾 |
| 5-7 | 看预算;预算紧就纯向量,预算松可以 POC GraphRAG |
| 8-10 | 上 GraphRAG,值得投入 |
| 11-12 | 不仅要 GraphRAG,还要考虑混合架构 |

## 四、5 个真实场景对比

把上面的框架用到具体场景,看怎么判。

### 场景 1:电商 FAQ 知识库

- 文档:500 篇产品 FAQ
- 查询:"退货政策是什么"
- **问题类型**: 0(相似度)
- **语料规模**: 0
- **关系密度**: 0(FAQ 里基本没实体关系)
- **查询模式**: 0(基本是单跳)
- **总分**: 0

**建议**:纯向量 RAG。GraphRAG 在这种场景就是烧钱。

### 场景 2:医疗文献检索

- 文档:2 万篇 PubMed 论文
- 查询:"治疗 X 病的药物 Y 和药物 Z 有什么相同靶点"
- **问题类型**: 2(多实体关系)
- **语料规模**: 2
- **关系密度**: 3(每篇论文 50+ 实体-关系)
- **查询模式**: 2(多跳 + 对比)
- **总分**: 9

**建议**:GraphRAG,优先 Local Search + 实体中心检索。

### 场景 3:法律合同审查

- 文档:500 份合同
- 查询:"A 公司和 B 公司在 2024 年签的所有合同里,违约责任条款有什么共同点"
- **问题类型**: 3(全局聚合)
- **语料规模**: 1
- **关系密度**: 2(合同里关系很多)
- **查询模式**: 3(总结 + 对比)
- **总分**: 9

**建议**:GraphRAG,Global Search 主导,Local Search 补充。

### 场景 4:客服工单库

- 文档:10 万历史工单
- 查询:"用户报修路由器掉线,之前怎么解决的"
- **问题类型**: 1(单实体 + 相似)
- **语料规模**: 3
- **关系密度**: 1(工单里实体关系不多)
- **查询模式**: 0(基本是相似度匹配)
- **总分**: 5

**建议**:边界场景。预算紧用纯向量 + 关键词混合;预算松可以 POC GraphRAG 但要先验证价值。

### 场景 5:企业内部 wiki

- 文档:3000 篇 wiki + 2000 人组织架构
- 查询:"新员工入职流程 + 涉及哪些部门 + 关键联系人"
- **问题类型**: 3(全局 + 多跳)
- **语料规模**: 1
- **关系密度**: 2(组织架构天然有图结构)
- **查询模式**: 2(多跳 + 总结)
- **总分**: 8

**建议**:GraphRAG,组织架构图 + wiki 文本双索引。

## 五、混合架构:不是二选一

现实里大部分生产系统是**混合架构**。GraphRAG 不会替代向量检索,而是补足它的盲区。

### 典型混合架构

```
用户 query
  ↓
[查询分类器 LLM]  ← 决定走哪条路
  ├── 类型 A(相似度/单文档 QA) → 向量检索 → LLM
  ├── 类型 B(实体/关系)         → GraphRAG Local Search → LLM
  └── 类型 C(全局/聚合)         → GraphRAG Global Search → LLM
```

### 简单一些的版本:向量召回 + 图精排

```
用户 query
  ↓
向量召回 top-50 chunks
  ↓
LLM 从 chunks 抽取候选实体
  ↓
在图上对这些实体做 1-2 hop 展开
  ↓
拿图谱上下文 + 原始 chunks → LLM 生成最终答案
```

这种架构的好处:**保留向量的召回广度,加上图的结构化精排**。LightRAG 默认就接近这种设计。

### 选混合架构的判断

| 条件 | 建议 |
|------|------|
| 80% 查询相似度,20% 全局/关系 | 混合架构,向量主导 |
| 50% 相似度,50% 关系/全局 | 混合架构,等权路由 |
| 80% 全局/关系 | GraphRAG 主导,向量补 |
| 不确定 | 先用查询分类器跑日志,看实际分布 |

## 六、7 条避坑清单

写给准备上 GraphRAG 的工程师。

**1. ❌ 不要为简单 FAQ 上 GraphRAG**
索引成本 100 美元,问题用 BM25 都能答,纯纯烧钱。

**2. ❌ 不要把 GraphRAG 当万能**
它解决的是「关系」和「全局」,不解决「幻觉」「事实性」「时效性」。这些问题得用别的方法。

**3. ❌ 不要忽视索引成本**
5k 文档索引可能烧 500 美元 token。生产前**先在 100 文档子集上跑一遍**,估算总成本再决定。

**4. ❌ 不要在增量更新上偷懒**
微软 GraphRAG 增量支持还不成熟,生产环境要么接受全量重建,要么自己写增量逻辑。**别假设"加文档很方便"**。

**5. ❌ 不要忽视 LLM 抽取错误**
实体识别错了,后面全错。要么用 few-shot prompt 提升准确率,要么对关键实体做人工校对。

**6. ❌ 不要在生产里只跑 GraphRAG**
至少留一条 fallback 通道(纯向量或 BM25)。GraphRAG 抽风时不能全站挂。

**7. ❌ 不要忽略查询延迟**
GraphRAG 比向量检索慢 2-5 倍。用户问"XX 怎么读"时,这种延迟差距会被明显感知。**路由要先做查询分类**,简单问题不要进图。

## 七、决策流程图(浓缩版)

```
开始
  ↓
语料 < 500 文档? 
  ├─ 是 → 纯向量 RAG,结束
  └─ 否 ↓
关系密度 < 5 关系/文档?
  ├─ 是 → 纯向量 RAG,结束
  └─ 否 ↓
查询主要是相似度?
  ├─ 是 → 向量 RAG,或混合架构(向量主导)
  └─ 否 ↓
需要全局/聚合/多跳?
  ├─ 是 → GraphRAG 主导 + 向量补
  └─ 否 → 混合架构(根据预算)
```

## 八、上 GraphRAG 前的 3 个验证步骤

不要直接上生产,**先做 POC**。

### Step 1:抽 100 文档子集跑全流程

```bash
# 准备子集
mkdir -p ./poc/input
# 抽 100 篇代表性文档
cp source/*.md ./poc/input/ | head -100

# 索引
python -m graphrag.index --root ./poc

# 测 10 个真实查询
python -m graphrag.query --root ./poc --method local --query "..."
python -m graphrag.query --root ./poc --method global --query "..."
```

### Step 2:跟纯向量对比答案质量

| 维度 | GraphRAG | 纯向量 RAG | 谁赢 |
|------|----------|------------|------|
| 全局问题 | 答得上来 | 答不全 | GraphRAG |
| 实体关系 | 答得准 | 答不全 | GraphRAG |
| 单文档 QA | 差不多 | 差不多 | 平 |
| 查询延迟 | 2-5x 慢 | 快 | 向量 |
| 索引成本 | 50-500 美元 | < 1 美元 | 向量 |

**如果 GraphRAG 在你的核心查询上没显著胜出,就别上**。

### Step 3:估算全量成本

| 文档量 | 索引 LLM 成本(估) | 存储成本 | 决策 |
|--------|---------------------|----------|------|
| 1k | 50-100 美元 | 1-2 GB | POC 可做 |
| 10k | 500-1500 美元 | 10-30 GB | 预算紧慎入 |
| 100k | 5k-2w 美元 | 100-500 GB | 必须 GraphRAG 才值 |
